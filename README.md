# 네이버 부동산 매물 모니터

관심 아파트 단지의 매매·전세 매물 물량과 호가 추이를 추적하는 개인용 모니터링 도구.

- 설계·계획: [`DEVELOPMENT_PLAN.md`](./DEVELOPMENT_PLAN.md) (§3·§6·§8은 2026-08-22 실측으로 갱신됨 — `CLAUDE.md` 참조)
- Claude Code용 컨텍스트: [`CLAUDE.md`](./CLAUDE.md)

## 빠른 시작

```bash
# 조사 1회를 끝까지 (평소에는 이것만)
python3 run_all.py
```

## 단계별 실행

```bash
# 1) DB 초기화 (최초 1회, 이미 data/monitor.db가 있으면 생략)
python3 -c "import sqlite3; sqlite3.connect('data/monitor.db').executescript(open('scripts/schema.sql').read())"

# 2) 매물 수집 (사용자 PC에서 실행 — 네이버는 클라우드/확장 접근을 차단함)
python3 collect_naver.py
#    → naver_data/<수집시각>/ 에 JSON 생성

# 3) DB 적재
python3 scripts/ingest.py naver_data/<수집시각>

# 4) 중복 판정 (규칙) — 애매 쌍은 data/ambiguous_<snapshot_id>.json 으로 나온다
python3 scripts/dedup.py <snapshot_id>

# 5) (선택) AI 판정 결과 반영
python3 scripts/dedup.py apply <snapshot_id> data/verdicts_<snapshot_id>.json

# 6) 정합성 진단
python3 scripts/integrity.py <snapshot_id> naver_data/<수집시각>/counts.json

# 7) 조사일 간 물건 연결 (신규/소멸/호가변동 기록)
python3 scripts/link_snapshots.py

# 8) 대시보드 생성 (dashboard/index.html — 브라우저로 열면 끝)
python3 scripts/build_dashboard.py
```

## 시간축은 조사일이다

등록일 기준으로 물량을 세면 팔리거나 내린 매물이 응답에서 빠지는 탓에 언제나 조사일에
가까운 쪽이 많아 보인다. 그래서 조사할 때마다 전량을 스냅샷으로 통째 저장하고, 조사일
축에서 비교한다. 소멸은 이 축에서만 관측되므로 실제 순증감과 호가 변동도 여기서만 나온다.
**`run_all.py`를 주기적으로 돌리는 것 자체가 데이터를 만드는 일이다.**

## 대시보드

`dashboard/template.html`이 앱이고, `build_dashboard.py`가 DB에서 뽑은 JSON을 끼워
`dashboard/index.html` 한 장으로 굽는다. 외부 CDN에 의존하지 않으므로 파일만 열면 동작한다.

- 좌측 **단지 ▸ 동 ▸ 평형 ▸ 타입 ▸ 층** 체크박스 트리와 매매/전세 토글이 아래 모든 차트·표를 함께 좁힌다. 선택은 localStorage에 남는다.
- 상단 **단지 범례**가 화면 전체에 하나뿐이고, 그것이 표시 스위치를 겸한다. 누르면 그 단지가 모든 차트·타일·표에서 빠지고 다시 누르면 돌아온다. 끈 단지도 범례에는 회색으로 남는다. 트리 선택이 *무엇을 보는가*라면 범례는 *그중 무엇을 그리는가*다.
- **색은 단지의 이름이다.** 색 슬롯은 이름순이 아니라 단지를 추가한 순서로 고정해서, 단지를 하나 넣어도 기존 단지 색이 밀리지 않는다.
- **평형 군집은 전용으로 묶고 공급으로 끊는다.** 전용면적 2㎡ 단일연결로 타입 가족을 모은 뒤, 그 안에서 공급면적이 1평 넘게 벌어지면 갈라낸다. 신현대 183(전용 170.4·공급 183.5)과 188B(전용 171.4·공급 188.9)는 전용이 1㎡ 차이라 붙어 있지만 평형은 두 평 다르다.
- **평형은 단지 안에서만 매긴다.** 전용면적이 비슷해도 전용률이 달라 공급 평형이 어긋나기 때문이다. 단지를 가로질러 묶었더니 LG한강자이 55평(전용 134·공급 179)이 래미안퍼스티지 52평(전용 136·공급 173), 팰리스 51평(전용 133·공급 168)과 한 덩어리가 되어 셋 다 52평으로 표시됐다.
- **타입 레벨**은 네이버 공급면적 표기(`179M`, `113L1`)를 그대로 쓰고 소수점 평형을 함께 적는다. 같은 34평 안에도 111A(33.8평)와 114D(34.6평)가 섞여 있다.
- **분양 관례명이 환산값과 다르면 관례명을 쓴다.** LG한강자이 50평대는 179M(공급 179.3㎡ = 54.2평)과 180L(180.2㎡ = 54.5평)인데 분양 때부터 55평형이었고 시장도 그렇게 부른다. `PYEONG_ALIAS`에 그 타입만 적어 두고, 환산값은 툴팁에 남긴다.
- 기본 선택은 단지마다 30평대다. 30평대가 없으면 30평 이상 중 가장 작은 평형을 고른다(LG한강자이는 28평 다음이 55평이라 55평).
- **호가와 등록 추이** — 등록일 축. 점 1개 = 물건 1개(y=그룹 최저 호가), 아래 패널은 같은 날 등록된 매물 수. 생존 편향이 있는 축이므로 카드에 그 한계를 적어 둔다.
- **매물 분포** — 호가 구간별 히스토그램(원시 매물 / 물건 두 겹).
- **물량 추이** — 조사일 축. 하한~상한 밴드. 조사일이 1개면 선 대신 숫자로 보여준다.
- **조사일별 호가** — 조사일마다 그때 살아 있던 물건만으로 낸 중앙값과 25~75% 구간.
- **조사일별 증감** — 신규(위)·소멸(아래). 단지를 새로 넣은 조사일의 편입 물량은 막대에서 빼고 아래에 따로 적는다.
- **물건 목록** — 정렬 가능한 표이자 차트의 표 대응물. 조사일이 2개 이상이면 Δ호가와 신규/편입이 채워진다.

조사일 축 차트는 DB의 `unit_links`/`unit_events`가 매긴 `unit_id`를 그대로 쓴다 —
대시보드가 매칭을 다시 계산하지 않으므로 표와 DB가 어긋날 일이 없다.
안 훑은 조사일은 0이 아니라 결측으로 그린다(0으로 이으면 단지를 추가한 날 물량이 솟은 것처럼 보인다).

`node scripts/domcheck.mjs`가 대시보드 스크립트를 최소 DOM 위에서 실제로 돌려
런타임 오류와 빈 차트를 잡는다. 템플릿을 고쳤으면 굽고 나서 이걸 돌린다.
- 색은 단지를 따라간다(필터를 바꿔도 단지 색은 그대로). 라이트/다크 모두 대응.

## 물량은 밴드로 읽는다

네이버 매물의 96%는 층이 정확한 층수가 아니라 저/중/고 대역으로만 표기된다. 그래서 같은 동·대역·평형·가격·방향의 여러 매물이 중복 등록인지 별개 세대인지 데이터로는 확정할 수 없다. 이 도구는 억지로 하나의 수를 만들지 않고 두 수를 함께 보여준다.

- **상한** — 네이버 동일매물묶기 결과
- **하한** — 자체 2차 병합 결과 (방향 불일치는 배제, 가격·설명 유사도로 점수화)

첫 스냅샷(2026-08-22): 원시 1174건 → 밴드 592~716건.

## 조사는 수동으로 돈다

필요할 때 직접 돌린다. 예약 스케줄러는 **2026-08-29에 걷어냈다.**

```bash
python3 run_all.py --note "메모"
```

조사일 축은 균등 간격을 요구하지 않는다. 각 조사는 실제 시각으로 그려지므로,
사흘 만에 돌리든 2주 만에 돌리든 추이는 그대로 읽힌다. 안 훑은 날은 0이 아니라
결측으로 그려서 빈 칸이 거짓말을 하지 않는다. 억지로 채운 값이 진짜 값보다 나쁘다.

수집은 반드시 사용자 PC에서 돈다. 네이버가 데이터센터 IP를 어떻게 대하는지 모르는 채로
클라우드 러너에서 돌리면 IP 차단 위험만 떠안는다 — 차단당하면 프로젝트 전체가 멈춘다.

### 왜 예약을 버렸나

이 노트북은 **Modern Standby(S0 저전원 유휴) 전용**이다. `powercfg /a` 상 S1·S2·S3가
모두 펌웨어 미지원이라, 작업 스케줄러의 `WakeToRun`이 기대대로 동작하지 않는다.
전원 정책을 맞춰도(절전 해제 타이머 AC·DC 양쪽 켬) 결과가 전원 상태에 좌우됐다.

2026-08-23 실측 3회 — **AC에서는 정시에 돌고, 배터리에서는 안 돈다.**

| 시험 | 전원 | 예약 | 실제 실행 | 결과 |
|---|---|---|---|---|
| 08:30 | 배터리 | 08:30 | 08:45 (덮개 열 때) | 시간 제한 강제 종료 |
| 09:45 | 배터리 | 09:45 | 09:49 (덮개 열 때) | exit 0 · 53초 |
| 10:10 | **AC** | 10:10 | **10:10:00 정각** | exit 0 · 52초 |

여기에 더해 작업이 시작돼도 몇 분 만에 도로 잠들어(08-23 08:45:04 시작 → 08:49:30 대기 진입 →
WSL VM 정지 → 09:15 강제 종료, 수집 폴더에 10개 중 9개만) 시스템을 붙잡아 두는
`SetThreadExecutionState` 래퍼가 따로 필요했다.

그리고 실제로 놓쳤다. 월·수·금 18:00으로 돌린 첫 주에 **2회 결측**:

| 조사일 | PC 상태 | 왜 안 돌았나 |
|---|---|---|
| 수 08-26 18:00 | 꺼짐 (08-25 12:55 ~ 08-28 12:27 이벤트 없음) | 꺼진 PC는 못 깨운다 |
| 금 08-28 18:00 | Modern Standby (12:30 ~ 23:02 연속) | 18:00에 대기 해제가 아예 안 찍혔다 |

`StartWhenAvailable` 따라잡기도 못 걸렸다 — 08-28에 부팅 **1분 뒤** 절전에 들어가 창이 닫혔다.

정리하면, 노트북이 예약 시각에 깨어 있을지를 통제할 수 없는 이상 예약은 신뢰할 수 없고,
신뢰할 수 없는 예약은 조용히 결측을 만든다. 조사 1회가 1분이면 끝나므로 손으로 돌리는 편이 낫다.

`data/schedule.log`는 그때의 실행 기록으로 남겨 뒀다. 이제 아무것도 여기에 쓰지 않는다.

예약용으로 켰던 배터리 절전 해제 타이머를 되돌리려면 (선택):

```powershell
$g = (powercfg /getactivescheme -split 'GUID: ')[1].Split(' ')[0]
powercfg /SETDCVALUEINDEX $g SUB_SLEEP RTCWAKE 0
powercfg /SETACTIVE $g
```

## 단지 추가

`collect_naver.py` 상단 `COMPLEXES` 딕셔너리에 단지명을 추가한다. 단지번호는 자동 검색되며,
실패하면 `"단지명": 12345` 형태로 직접 지정한다. 현재 대상은 래미안신반포팰리스(108228),
래미안퍼스티지(23759), 삼성힐스테이트2단지(24008), LG한강자이(3143),
신현대(현대9,11,12차)(3037), 한가람(867) 여섯 곳이다.

흔한 이름은 번호를 직접 적는다. "신현대"만으로 검색하면 전국에 열 곳 넘게 나와
자동 검색이 압구정 신현대를 고른다는 보장이 없다.

단지를 추가하거나 뺀 조사일에는 그 단지 물건이 전부 신규/소멸로 보일 수 있다.
`link_snapshots.py`가 이를 구분해 편입분은 `enter`로 남기고, 안 훑은 단지는 소멸로 세지 않는다.
집계할 때 `enter`는 신규에서 제외한다.
